# Tasks.org tasks on the calendar, with completion and Undo

KashCal now reads tasks with a due date from the Tasks.org ContentProvider (`content://org.tasks.api/v0`) and shows them as a third `DisplayEvent` source, `DisplayEvent.Task`, next to Room and device events. Tasks are never stored. A ContentObserver on `/v0/tasks` bumps a change signal that the view flows and the month dots react to. Users complete or reopen a task from a quick-view sheet or from a new compact `TaskCard` with a checkbox. A snackbar offers Undo, and for a repeating task Undo restores the schedule snapshot taken before completing. The diff also changes the dots rebuild so it no longer clears the dots first.

Watch for: tapping a checkbox twice quickly on a repeating task advances the series and then reports "Task reopened" without undoing the advance (**confirmed**). The two writes are not serialized, so even for plain tasks the final state depends on which IO write lands first (**confirmed**). The list checkbox is enabled whenever READ is granted, even without WRITE, and Settings never asks for WRITE again (**confirmed**). The checkbox has no accessible label (**confirmed**). Paging can return the same task twice, which crashes the keyed LazyColumns (**likely**, needs >1000 tasks in range plus a concurrent sync).

**Verdict**: NEEDS_CHANGES

## High-level view

`DisplayEvent.Task` places a task the way Room places an event. A timed task is a zero-length point at its due time. An all-day task's local due date becomes UTC midnight to the last millisecond of that UTC day. The provider query uses the local day bounds against the raw `due_date`, which matches the Tasks.org rule that all-day dates are local. Every `when` over `DisplayEvent` now handles Task. The Planner's "Different this week" box and the month dots take tasks with no Task-specific decision.

Completion is optimistic in two places, and neither handles concurrency. `TaskCard` flips a local override and reverts it only when the write is refused. The ViewModel launches each write as an independent coroutine on the IO dispatcher, with no per-task ordering and no in-flight guard. On repeating tasks this matters because Tasks.org advances the series on every completion. The quick-view sheet ignores the write result entirely.

Undo writes back what KashCal saw before the change. For plain tasks it only resets `completed_at`. Tasks.org cascades completion state to subtasks and parents in both directions, so Undo does not restore the subtask state it reports restoring.

The permission and lifecycle handling covers the startup path: revoking a permission kills the process, and `TasksOrgManager.initialize` then turns the source off. It does not cover a missing WRITE permission while READ is granted, or Tasks.org being uninstalled and reinstalled while KashCal runs.

Paging walks `limit=1000&offset=n` pages ordered by `_id` without de-duplicating. If a row's due date moves into the range between pages, the next page repeats a row. Day lists, the agenda and search key their items by task id, so the repeated row is a duplicate key.

The dots change replaces the dots in one state update instead of clearing first, which fixes the blinking. Rebuilds still are not cancelled, and each KashCal write now triggers two of them (the immediate bump, then the observer about a second later).

<summary>Issues (14)</summary>

1. **Double-tap on a repeating task** — a second tap while the first write is in flight sends `completed_at=0`, which does nothing on the already-advanced series, and the snackbar says "Task reopened". Disable the checkbox while a write for that task is in flight, or treat unchecking a just-completed repeating task as running its Undo.
2. **Unordered concurrent writes** — `setTasksOrgTaskCompleted` launches each toggle on the IO dispatcher with no ordering, so complete then reopen can land in reverse. Serialize writes per task id (a `Mutex` or a single-consumer channel) or block re-entry until `onResult` fires.
3. **Stale `onResult` clobbers a newer tap** — a late `onResult(false)` from the first write clears the override set by a second tap. Track a request token in `TaskCard` and ignore results from older requests.
4. **WRITE permission not gated in lists** — `TaskCard` enables the checkbox from `!task.isReadOnly` only, and Settings checks only READ, so a READ-only grant gives a live checkbox that always fails. Pass `canComplete` (WRITE granted and not read-only) into `TaskCard` as the quick view does, and re-request WRITE in Settings when it is missing.
5. **Quick view ignores refusal** — `MainActivity` updates `taskQuickViewEvent` optimistically and passes no `onResult`, so a refused write leaves the sheet showing the wrong state. Pass `onResult` and revert the sheet's copy when the write is refused.
6. **Undo does not restore subtasks or parents** — per the provider docs, completing cascades to subtasks and reopening un-completes parents, but `SetCompletedAt` undo writes only the task's own `completed_at`. Either document that Undo is partial, or snapshot and restore the affected subtasks and parent.
7. **Checkbox has no accessible label** — the `TaskCard` checkbox is a separate TalkBack node inside the clickable card, announced only as "Checkbox, not checked". Give it a `contentDescription`/`stateDescription` that includes the task title, or make the whole row `toggleable` with `Role.Checkbox` like `TaskCompletionRow`.
8. **Duplicate rows from paging** — `readPages` can return the same task twice when rows shift between pages, and that crashes `items(key=…)` in `DayEventsSheet`, agenda and search. Apply `distinctBy { it.id }` in `getTasksDueInRange`, or bound the loop by `EXTRA_TOTAL_COUNT`.
9. **Search results never refresh** — search is a one-shot snapshot, so after completing a repeating task from search the row stays on the old occurrence and a second tap hits issue 1. Re-run the active search on the Tasks.org change signal, or drop the checkbox from search results.
10. **Tasks fill "Different this week"** — all-day tasks (and tasks repeating monthly or less often) pass `isStripItem` and appear in the Planner summary box, completed ones included. Exclude `DisplayEvent.Task` in `summaryKind`, or confirm this is intended.
11. **Dots rebuild races** — `buildEventDots` is not cancelled, so an older rebuild can overwrite a newer one, and each write now triggers two rebuilds over 13 months of Room, device and provider queries. Keep a `dotsJob` and cancel it before relaunching, and skip `notifyChanged()` or the observer bump for KashCal's own writes.
12. **Re-enable after reinstall** — after Tasks.org is reinstalled while KashCal runs, the source is still on without the permission. The screen says "Tap Enable to grant access", but tapping the switch turns it off. Make the message a button that launches the permission request, or turn the source off when the read fails with `SecurityException`.
13. **Contract docs disagree with provider** — `TasksOrgContract` says a collection returns "at most MAX_LIMIT rows", but the provider docs say the default is 100 with no maximum. Reword the comment so `1000` reads as KashCal's chosen page size.
14. **Upstream polish** — the list refresh button reuses `cd_refresh_calendars` ("Refresh calendars"), `WidgetDataRepository.toWidgetEvent` has an early `return null` that makes its two `Task -> return null` branches dead, and the `DisplayEvent.Task` KDoc says only the quick view toggles completion. Add a task-specific content description, drop the redundant branches, and update the KDoc.

### Optimistic checkbox and repeating-task completion

`TaskCard` keeps `checkedOverride` in a `remember` keyed on `stableKey`, `completedAt` and `dueTs` (TaskCard.kt:67), so the re-query after a write resets it. The trouble is the window before that re-query.

```
tap 1 (open → checked)   override=true   launch setCompleted(task, true)     [IO]
tap 2 (checked → open)   override=false  launch setCompleted(task, false)    [IO]
                                         └─ undo = SetCompletedAt(id, null)  (stale task)
provider: tap 1 advances the series (due moves forward, completed_at=0)
provider: tap 2 writes completed_at=0    → no-op
snackbar: "Task reopened" + Undo(SetCompletedAt null)   ← replaces the RestoreSchedule Undo
```

The provider docs say "Retrying a completion advances the series again", and `TasksOrgCoordinator.setCompleted` (TasksOrgCoordinator.kt:63-70) chooses the undo strategy from the `TasksOrgTask` captured at tap time. Uncheck-before-requery therefore looks like a revert, but the series has silently moved forward and the only Undo that could bring it back has been replaced (**confirmed**). Search results make this easier to hit because they never re-query (HomeViewModel search writes `searchResults` once; nothing re-runs it on the change signal). The completed repeating row stays checked indefinitely, so the next tap always takes the "reopen" path (**confirmed**).

The writes themselves are unordered. `setTasksOrgTaskCompleted` (HomeViewModel.kt:4434-4442) does `viewModelScope.launch { withContext(ioDispatcher) { … } }` per tap. Two taps become two concurrent IO jobs, and the repeating path even does a `getSchedule` read first, which delays the first write. Complete then reopen can reach the provider in reverse order, ending completed while the card shows open until the re-query flips it (**confirmed**). The `onResult` callback has a smaller version of the same problem. A late `onResult(false)` sets `checkedOverride = null` even if a newer tap already set it (TaskCard.kt:102-104) (**confirmed**).

The quick view in `MainActivity` (MainActivity.kt:1133-1148) calls `setTasksOrgTaskCompleted(shown.task, completed)` without `onResult` and rewrites `taskQuickViewEvent` immediately. A refused write shows the failure snackbar while the sheet keeps the optimistic "Completed" state (**confirmed**). The Undo snackbar renders in HomeScreen's host, under the modal sheet that stays open for a plain task, so Undo is likely hard to reach until the sheet is dismissed (**likely**).

### Undo and Tasks.org's cascade semantics

`RestoreSchedule` sends `due_date` and `start_date` with their all-day flags. That matters because the provider docs say an omitted flag keeps the row's value and a lone `due_date` drags a nearby start date with it. The non-repeating path is lossy. Per the docs, writing `completed_at` "cascades to subtasks either way, un-completes parents when uncompleting". Completing a parent from KashCal completes its open subtasks, and Undo then reopens all of them, including subtasks that were already completed before the tap. Reopening a subtask reopens its completed parent, and Undo re-completes only the subtask (**confirmed** from the provider docs; `SetCompletedAt` writes only the task's own id). KashCal does not show subtask relationships, so the user has no way to see the side effect.

### Permission gating for completion

The quick view computes `canComplete` from WRITE permission plus `isReadOnly`. `TaskCard` uses `enabled = !task.isReadOnly` only (TaskCard.kt:100). Settings requests READ and WRITE together, but enables the source and hides the request once READ is granted (SettingsRoute.kt:324-330, 747). A user who grants READ and denies WRITE gets checkboxes that flip, fail, and show "Couldn't update task" on every tap, with no path in Settings to grant WRITE later (**confirmed**).

Uninstalling Tasks.org while KashCal runs drops the permission without killing KashCal. The pref stays on, the observer stays registered, and every query fails silently through `guarded`. After a reinstall the Tasks.org screen shows `tasks_org_permission_required` ("Tap Enable to grant access") next to a switch that is already on. Tapping it calls `onToggle(false)`, so the user must tap twice and gets no prompt on the first tap (**confirmed**).

### Paging and duplicate list keys

`readPages` (AndroidTasksOrgRepository.kt:125-141) walks `offset += count` until a short page. The provider orders by `_id` and gives no snapshot across pages. If a lower-id task's due date moves into the queried range between two page fetches (a sync running, or the user editing in Tasks.org), every following row shifts by one and the boundary row comes back on the next page. `getTasksDueInRange` does not de-duplicate, and the lists key by task id: `DayEventsSheet` uses `stableKey`, the agenda `task_<id>_<day>`, search `task_<id>`. Compose throws on duplicate keys (**likely**; it needs more than 1000 matching tasks, which the 13-month dots range and the 2-year search range make more reachable). `distinctBy { it.id }` before the sort removes the crash.

### Accessibility of TaskCard

The card is `.clickable` (merging its text), and the `Checkbox` is its own toggleable node without a label. TalkBack reads the card as "title, time" and the checkbox separately as "Checkbox, not checked", with no task name. Completion state on the card itself is shown only by strikethrough, because `TaskCard` drops the ☐/☑ prefix (**confirmed**). The quick view's `TaskCompletionRow` handles this correctly with `toggleable(role = Role.Checkbox)` on a row that includes the label. `TaskCard` should either label the checkbox (`Modifier.semantics { contentDescription = title }` plus the checked state) or follow the same pattern. A disabled checkbox on a read-only list also gives no reason for being disabled.

### Where tasks flow into existing features

Two existing features take tasks without a guard. `differentThisWeek` lists any all-day item through `isStripItem`. `ownRrule` returns the task's RRULE, so every non-recurring all-day task (completed ones included), and tasks repeating monthly or less often, show up in the Planner's "Different this week" box (**confirmed**). This changes what an existing feature shows, so it needs a deliberate decision. The month dots also include completed tasks, which may or may not be intended.

Widgets exclude tasks but still pay for them. `getDisplayEventsGroupedByDayOnce` queries `getLists()` and the tasks before `WidgetDataRepository` drops them. Every Room emission in the range flows also re-runs the provider queries, because `queryTaskEvents` sits inside the `combine` lambda. Both are binder calls on hot paths, low severity.

### Dots rebuild

The change to `observeDeviceCalendarChanges` (HomeViewModel.kt:1286-1303) removes the clear-before-rebuild, which fixes the blinking. `buildEventDots` still launches an uncancelled job that replaces `eventDots` wholesale when it finishes. A KashCal write bumps `changeSignal` from `notifyChanged()` right away and again from the observer about one second later. The docs note "a client that writes wakes itself". So every toggle causes two 13-month rebuilds, and if they finish out of order the older result wins (**likely**; the race existed before, but this diff doubles how often it happens). Separately, `_changeSignal.value++` runs from both the IO thread (coordinator) and the main thread (observer) and is not atomic. Use `update { it + 1 }`.

This fix also changes the device-calendar path, so it may be worth landing as its own commit for the upstream maintainer.

### Test coverage

Repository, coordinator and `formatTaskCardTime` tests cover mapping, bounds, paging continuation, refusal, both Undo strategies and all-day placement.

Not tested: `HomeViewModel.setTasksOrgTaskCompleted` and its Undo snackbar wiring, the `TaskCard` override and reset behavior, rapid or concurrent toggles, `TasksOrgManager` (observer registration, turning the source off without permission), the dots rebuild change, the widget exclusion, the Settings permission flow, and the Planner summary with tasks present.
